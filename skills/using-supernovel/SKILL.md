## 规则

**在任何回复或行动之前，先调用相关或被请求的技能**——包括澄清问题、探索文件或检查项目。如果结果证明不适用，你可以不继续使用它。

然后宣布"正在使用 [技能名] 来 [目的]"并严格遵循该技能。如果技能有检查清单，为每项创建一个待办任务。

## 技能优先级

当多个技能适用时，流程技能优先——它们设定方向，然后写作技能执行。

- "我想写一个小说" / "让我们写个故事" → supernovel:brainstorming 优先
- "设计世界观" / "我需要一个设定" → supernovel:worldbuilding
- "我需要角色" / "设计主角" → supernovel:character-design
- "规划情节" / "设计故事结构" → supernovel:plot-architecture
- "细化大纲" / "逐章规划" → supernovel:chapter-outlining
- "写第 N 章" / "开始写作" → supernovel:drafting
- "检查一致性" / "审查这一章" → supernovel:consistency-check
- "修改/编辑" / "润色对话" → supernovel:revision
- "完成" / "统稿" / "交付小说" → supernovel:finishing

## 危险信号

以下想法意味着停下来——你在自我合理化：

| 想法 | 现实 |
|------|------|
| "我直接开始写吧" | 你需要先有经批准的大纲。检查技能。 |
| "想法已经够清楚了" | 技能告诉你如何澄清。先检查。 |
| "这是个简单的故事" | 简单的故事也需要结构。使用技能。 |
| "我已经了解这个角色了" | 先写档案。记忆会模糊。技能能防止这一点。 |
| "让我先写一章试试" | 没有大纲就写作 = 必定返工。 |
| "一致性以后再修" | 不一致会累积。现在就检查。 |
| "用户想看到进展" | 没有结构的进展是混乱。技能能防止这一点。 |
| "我不需要故事圣经" | 到第 5 章你一定会自相矛盾。 |
| "这不需要正式的技能" | 如果技能存在，就使用它。 |
| "我记得这个技能" | 技能会更新。读当前版本。 |
| "技能太重了" | 简单的事情会变复杂。使用它。 |
| "让我先做这一件事" | 在做任何事之前先检查。 |

## 故事圣经

每个小说项目都必须在项目根目录维护一个 `story-bible.md`。这是所有故事元素的唯一真相来源：世界观、角色档案、情节线索、伏笔、时间线和风格指南。

**任何细节在写入故事圣经之前都不是"正式的"。**

开始新项目时，如果 `story-bible.md` 不存在，worldbuilding 技能会创建它。之后每个技能都从故事圣经读取并更新它。

## 平台适配

- Claude Code：使用基于 hook 的注入（hooks/hooks.json）
- Kimi Code：使用 sessionStart.skill 注入（原生）

## 用户指令

用户的直接请求优先于技能，技能优先于默认行为。只有当你的用户明确告诉你跳过时，才可以跳过技能工作流。
